# 电商商城系统 · 项目前提信息包

> 模拟项目：云栖优选 B2C 商城。本文中的公司、指标、故障数据均为演练用模拟数据，不对应真实业务。

## 1. 项目背景

云栖优选成立于 2019 年，从生鲜自营起步，逐步扩展为「自营 + 平台」的 B2C 商城。2026 年平台有注册用户 480 万、月活 96 万、日均订单 1.8 万单，年 GMV 约 3.2 亿元。业务增长点集中在大促（618、双 11、年货节）和直播带货，大促峰值的下单请求是日常的 8～10 倍。

现有系统由 2022 年的一次单体拆分而来：商品、购物车、订单、支付、库存、售后拆成独立服务，但库存扣减仍保留「Redis 预扣 + MySQL 落库」的双写结构。2025 年双 11 曾出现 23 件超卖和 4 笔重复支付回调，成为今年大促保障的头号风险。

本项目要解决的核心问题是：**在大促高并发下保证「库存不超卖、支付回调不重复、订单状态可对账」**，同时把下单链路 P99 控制在 500ms 以内。

## 3. 范围与边界

**范围内**：商品与 SKU、购物车、下单、库存扣减、支付与回调、订单状态机、取消/退款申请、优惠券试算、对账文件。

**范围外**：仓储 WMS 的拣货/发货执行（外部系统，只通过 MQ 接收发货回执）、供应商结算、物流轨迹（第三方快递查询）、直播推流。

## 5. 核心流程与状态机

### 5.1 下单主链路

1. 顾客提交订单 → 订单服务校验商品、价格、优惠券、风控。
2. 库存服务预扣：Redis `DECRBY` 扣减可售库存，写预扣流水（`stock_reserve`）。
3. 订单落库，状态 `PENDING_PAYMENT`，返回支付参数。
4. 支付网关异步回调 → 支付服务验签、幂等去重 → 更新支付单。
5. 支付成功事件投递 MQ → 订单服务把订单推进到 `PAID`，库存服务把预扣转为实扣。
6. WMS 消费发货单 → 回执 `SHIPPED` → 订单 `SHIPPED` → 顾客确认 `COMPLETED`。

### 5.2 订单状态机

`PENDING_PAYMENT → PAID → SHIPPED → COMPLETED`；取消分支：`PENDING_PAYMENT → CANCELLED`（超时 30 分钟自动取消）；售后分支：`PAID/SHIPPED/COMPLETED → REFUNDING → REFUNDED`。

约束：只有 `PENDING_PAYMENT` 和 `PAID` 可取消；`SHIPPED` 之后只能走退货退款；任何状态变更必须写 `order_status_log`。

### 5.3 库存扣减（当前实现，已知有缺陷）

```
# inventory-service 伪代码（2026-10 版本）
stock = redis.get("stock:" + sku_id)
if stock is None or int(stock) < qty:
    raise StockNotEnough
redis.decrby("stock:" + sku_id, qty)
row = db.query("select stock from inventory where sku_id = ?", sku_id)
if row.stock < qty:
    redis.incrby("stock:" + sku_id, qty)   # 补偿
    raise StockNotEnough
db.execute("update inventory set stock = stock - ? where sku_id = ?", qty, sku_id)
```

缺陷：Redis 预扣与 DB 扣减不是原子操作；DB 的 `select` 与 `update` 之间没有行锁/版本号；补偿失败时 Redis 与 DB 长期不一致；MQ 重试会重复执行扣减。

## 8. 非功能与可观测性

- 下单、支付回调、库存扣减三个接口必须有 RED 指标（Rate/Error/Duration）。
- 关键日志字段：`trace_id`、`order_id`、`sku_id`、`channel_txn_id`。
- 告警：库存为负立即 P0；支付回调失败率 > 1% 持续 5 分钟 P1；MQ 积压 > 1 万 P1。
- 所有写接口必须支持幂等键（`Idempotency-Key` 或业务唯一键）。
- 敏感数据：手机号、收货地址在日志和客服后台脱敏。

## 9. 已知风险与历史问题

| 风险 | 证据 | 影响 | 当前缓解 |
| --- | --- | --- | --- |
| 库存双写不一致 | 2025 双 11 超卖 23 件 | 客诉、赔付 | 人工对账 + 补库存 |
| 支付回调重复 | 2026 春节 4 笔重复入账 | 重复发货/退款 | 人工冲正 |
| 订单状态抖动 | 对账差异 0.18% | 客服查询不准 | T+1 对账脚本 |
| 秒杀热点 key | 单 SKU 6,000 QPS | Redis 单分片打满 | 本地缓存 + 分段库存 |
| 大促容量 | 压测 8,000 QPS 下 P99 1.2s | 下单超时 | 限流 + 排队 |

## 10. 验收与演练关注点

1. 用 8,000 QPS 压测下单链路，P99 < 500ms，错误率 < 0.1%。
2. 模拟支付回调重复投递 10 次，只产生 1 条支付成功记录、1 次库存实扣。
3. 模拟 Redis 扣减成功、DB 扣减失败，验证补偿或对账能发现差异。
4. 库存为负时告警在 1 分钟内触发。
5. 订单状态机非法流转（如 `CANCELLED → PAID`）必须被拒绝并记录审计日志。

## 11. 给智能体的前提假设

- 本文数字是演练基线，不是实时数据；涉及金额一律以「分」为单位。
- 生产变更必须走「先加开关 → 灰度 1% → 观察 30 分钟 → 放量」。
- 任何库存/支付相关修复，必须同时给出回滚方案和对账 SQL。
- 不允许在没有幂等键的情况下重试写接口。
